油气储运「NF」分发部署方案

自包含发行包 · 分层一键安装向导 · 三发行变体 · 配套文档之分发篇

资产全打包 环境解压后构建 离线 wheels 安装自检 更新与卸载

一、分发篇定位：解决「最后一公里」

本文是 NF 文档系列的第三篇：《痛点与解决方案汇总》（定义务篇）回答「做什么」，《实施路线图》（行动篇）回答「怎么一步步做」，本文（分发篇）回答「做出来之后怎么发到其他设备上」。目标形态一句话：把 NF 的全部智力资产打成一个自包含压缩包，目标设备解压后由分层一键安装向导引导构建可运行环境——账号注册、环境安装等机器相关事项在解压后由用户选择完成。

分发设计总原则：

  • 凡是「文件」的都进包——知识库卡片、事件库、引擎源码、基准题、任务定义、身份模板，全部是可拷贝的文件资产；
  • 凡是「注册 / 凭据 / 运行时」的留给向导——Python 环境、MCP 注册、定时任务注册、账号登录、个人身份选择，在目标设备上现场生成；
  • 资产与运行环境分离——包是「内容与逻辑」，向导负责「接线通电」；同一种资产可按用户选择构建出全功能、纯离线或自定义的运行形态。

二、资产切分：什么进包、什么留在解压后

按「文件 vs 注册/凭据/运行时」切分 NF 的全部组成，得到两张清单——这是整个分发方案的地基。

表 1 可进包的智力资产清单（7 项）
资产 进包形态 说明
计算引擎 engine/：源码 + requirements.txt + 离线 wheels 依赖包 源码天然可拷；wheels 是关键技巧——把依赖的安装包预下载进包，目标机器无网也能装
基准回归题 data/baselines/ 20–30 道手算例题进包，安装后立即自验「不乱给结果」，同时充当装机验证
专业知识库 skill/references/ 卡片目录 全部带溯源的转正卡片，规范 / 公式 / 介质 / 设备 / 案例分类存放
事件库 data/events.db（SQLite 单文件） 含已分级的历史事件与辟谣链，新设备开箱即有积累，而非从零重建
定时任务 jobs/daily-task.json（任务定义）+ jobs/scripts/（五件事执行脚本） 注册状态进不了包，但定义与脚本可以——向导照着定义在目标设备一键重建注册
身份记忆 identity/identity-template.md 模板 个人身份不硬编码（防多人共用串身份），模板进包，由向导引导用户选择后写入本机
安装向导自身 install.ps1 / install.sh（包根目录） 连同 update.ps1、uninstall.ps1 一起随包分发
表 2 解压后由向导引导构建的事项（3 类）
类别 具体事项 为何不进包
运行时环境 Python 解释器、虚拟环境 venv、依赖安装（wheels 离线 / pip 在线） 与目标机器架构强相关，打包内嵌体积大且跨平台易错
平台注册 MCP 服务注册、每日定时任务注册、TeleAgent Desktop 本体安装与账号登录 注册状态存于平台内部，属于「接线」而非「资产」；凭据必须现场产生
个人身份 身份四选一（学生/教师/运维/设计）、长期记忆初始化 跟人不跟包——多人共用同一安装包时避免身份串用

切分结论：NF 的全部「智力资产」（引擎逻辑、知识、基准、任务定义）100% 可进包；留给解压后的只有运行时、平台注册与个人身份三类机器/用户相关事项。「解压即得全部内容，向导负责接线通电」由此成立。

三、发行包目录结构

标准发行包（解压前为一个 zip）的内部结构如下——三份文档约定的全部机制都能在这棵目录树中找到对应位置：

NF-release/
├─ install.ps1              # 一键安装向导（Windows）
├─ update.ps1               # 知识库增量更新（不动引擎）
├─ uninstall.ps1            # 卸载（回收站式移除）
├─ manifest.json            # 包清单：版本、卡片数、校验和、适用平台
├─ skill/                   # ① 薄壳主 Skill
│  ├─ SKILL.md              #    仅身份路由+工作流（数百行）
│  └─ references/           #    知识外置，按需读取
│     ├─ standards/         #    规范卡片（含版本状态链）
│     ├─ formulas/          #    公式卡片（带溯源）
│     ├─ media/             #    介质物性卡
│     ├─ equipment/         #    设备档案卡
│     ├─ cases/             #    工程案例卡（脱敏）
│     └─ workflows/         #    决策树与检查清单模板
├─ engine/                  # ② 计算引擎（MCP）
│  ├─ src/                  #    源码：水力/热力/强度/阴保模块
│  ├─ requirements.txt      #    依赖清单
│  └─ wheels/               #    离线依赖包（离线版才有）
├─ data/                    # ③ 数据资产
│  ├─ baselines/            #    基准回归题（20–30 道）
│  └─ events.db             #    事件库（SQLite，含分级与辟谣链）
├─ jobs/                    # ④ 定时任务定义
│  ├─ daily-task.json       #    每日五件事的任务定义
│  └─ scripts/              #    自检/回归/扫描/报告脚本
└─ identity/                # ⑤ 身份模板
   └─ identity-template.md  #    四选一模板，向导引导填写

设计要点：manifest.json 记录包版本、卡片数量、关键文件校验和与适用平台——安装向导、更新脚本与后续排查都以它为准；目录即架构——skill / engine / data / jobs / identity 五个子目录与实施路线图的「三件套 + 双库 + 任务」一一对应，看目录即懂系统。

四、一键安装向导：八步流程

解压后运行 install.ps1，向导按八步推进。每一步都检测先行、选择在后：缺什么列什么，用户按需选择构建范围，任何一步失败不中断整体——进入降级安装并在安装报告中标注。

  1. Step 0 · 环境检测

    检测 TeleAgent Desktop 是否安装、Python 是否可用、网络是否连通；缺项逐条列出并给出获取指引，不中断。

  2. Step 1 · 安装范围选择

    三选一：全功能（引擎+双库+每日任务）/ 仅本地核心（无每日扫描，纯离线可用）/ 自定义（勾选计算引擎、定时任务、事件库、每日报告各项）。

  3. Step 2 · 部署 Skill

    复制薄壳 Skill 与知识库卡片至本机用户技能目录，登记为可用 Skill。

  4. Step 3 · 构建引擎环境

    创建虚拟环境 venv → 优先从包内 wheels 离线安装依赖 → 无 wheels 则在线 pip 安装 → 两者皆不可用时输出手动安装指引。检测到 TeleAgent Desktop 未安装时，此处弹出下载安装指引并提示账号登录由用户自行完成。

  5. Step 4 · 注册 MCP

    将计算引擎注册为本机 MCP 服务（stdio，指向 engine/）；若平台仅开放设置界面，则写好配置文件并弹出精确到点击步骤的指引，由用户点一次「启用」完成。

  6. Step 5 · 重建定时任务

    读取 jobs/daily-task.json 定义，在本机注册每日五件事任务；按 Step 1 的选择可跳过。

  7. Step 6 · 身份初始化

    交互选择身份（学生/教师/运维/设计）写入本机记忆；可跳过——跳过则首次使用时由 Skill 主动询问，体验一致。

  8. Step 7 · 安装自检与报告

    验证 Skill 可发现、MCP ping 通、运行一道基准题并与标准答案比对；全项通过才算装好。输出《安装报告.html》：成功项、跳过项、降级项与补装指引一屏呈现。

设计亮点：装机验证复用质量闸门。Step 7 的基准题比对，就是实施路线图阶段 3 的「基准回归」机制在新设备上的单点复用——任何一台机器装完 NF，跑一道题对答案，通过才算安装成功。质量保证与分发验证在此合流：同一套基准题既证明引擎「不乱给结果」，也证明这台机器「装对了」。

五、三发行变体：同一结构，按需填充

三个变体共享同一目录结构与安装流程，差别只在填充物与用途定位——做一次结构设计，覆盖三类受众。

表 3 三发行变体对比
变体 包体量级 与标准结构的差异 适用对象
在线安装版 小（MB 级） wheels 目录为空，Step 3 走网络安装 网络条件好的办公室、教研室场景
离线完整版 大（百 MB 级） 内嵌全量 wheels，全程无网可装 发给学生、现场人员等无技术背景/弱网环境用户，最稳
团队源版 中 在线版结构 + git 版本化管理，作为知识库官方源 教师团队共建，其他设备 git pull 增量更新

变体选择的决策逻辑：

  • 不确定对方网络与技能水平 → 离线完整版，牺牲包体换确定性；
  • 对象是会用 git 的教师团队 → 团队源版，卡片校核走提交评审，知识库持续演进不分叉；
  • 其余常规场景 → 在线安装版，包小好传。

六、更新与卸载：分发不是一次性动作

分发解决「第一天能用」，而 NF 是每日迭代的活库——A 设备每天新增卡片与事件，B 设备的副本会日渐过时。因此发行包必须配套更新通道与干净的退出机制。

表 4 更新通道与适用场景
通道 机制 适用
update.ps1 增量包 只携带 manifest 标记之后新增/变更的卡片与事件库差异，更新时不动引擎与已注册任务 在线/离线版的常规更新
git pull（团队源版） 知识库 git 化，各设备拉取官方源最新提交，历史可回溯 教师团队共建场景
整包重发 积累到一定量级后重新打离线完整版分发 弱网环境、重大版本升级

update.ps1 的安全规则：

  • 只增量、不覆盖用户本机差异——用户本机新写的个人记忆、易错点记录绝不回滚；
  • 校验和核对——更新前按 manifest 校验文件完整性，不一致即中止并列出差异；
  • 更新后自检——复用安装向导 Step 7 的基准题比对，确认更新未破坏引擎正确性。

uninstall.ps1 的卸载原则：

  • 回收站式移除——文件移入回收站而非直接删除，给用户反悔余地；
  • 注册反解——撤销 MCP 注册与定时任务注册，但不触碰平台本体与其他 Skill；
  • 用户数据保留——个人身份记忆与个人沉淀内容默认保留并提示位置，由用户自行决定去留。

七、三条诚实边界

① TeleAgent Desktop 本体进不了包：软件安装与账号登录是平台层事项，向导只能检测到「未安装」并给出下载安装指引——这一步用户绕不开，属于「一键」成色的天然上限。

② 平台注册的自动化程度取决于平台接口：若桌面端开放命令行/配置文件级注册，Step 4/5 全自动；若仅开放设置界面，则降级为「半自动」——配置写好、指引精确到点击步骤，用户点一次「启用」完成。方案按两种情形都做了设计。

③ 离线 wheels 与包体是一对矛盾：用「三发行变体」化解而非硬塞一个大包——离线完整版体积代价只由需要它的受众承担。

与其他分发方式的衔接（本方案为基座，按需叠加）：

  • Git 仓库＝在线安装版结构 + git 化（即团队源版）；
  • 共享 MCP 服务器＝向导 Step 4 改为「填远程 URL」的变体，适合教研室统一引擎版本（需重新评估数据边界）；
  • 中心—辐射同步＝团队源版 + 一台常开主机作官方源，其余设备定期拉取快照，解决多设备更新分叉。
